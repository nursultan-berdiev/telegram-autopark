# 07 — Фазы исполнения, зависимости, приёмка

Полный рефактор — цель; работу дробим на фазы, чтобы каждая давала рабочее состояние и зелёные
тесты. Одна фаза может делиться на несколько веток/коммитов. Зависимости строгие: фаза N+1
начинается после приёмки N (кроме явно параллельных).

> **Железо (внешняя зависимость, важно для приёмки).** На момент планирования к нашему Traccar
> **не подключена ни одна из 5 машин**: 139 откачена на SinoTrack и сдана 01.09 11:28; номера
> SIM машин 137/138/195/637 неизвестны (нужны, чтобы их переключить); реле блокировки
> подтверждено **только на 139**. Поэтому приёмка по коду/логике идёт **на моках +
> Traccar Client (OSMAnd)** без живого трекера, а железный сквозной прогон блокировки вынесен в
> отдельную веху **Фаза 5-HW**, гейтящуюся внешней зависимостью (получить SIM + доступ к авто с
> реле). Разработку ожиданием железа не блокировать.

## Фаза 0 — Монорепо + переезд домена
**Шаг 0 (обязателен первым):** текущее дерево грязное — на ветке `feature/overdue-partial-payments`
~49 изменённых/неотслеживаемых файлов (Dockerfile, docker-compose.yml, bot/scheduler.py,
bot/services/reminders.py, миграции 0002–0005, tests/* — untracked), на `origin` только
`2d5d0a8 first commit`. **Закоммитить и запушить текущее рабочее состояние** до любых `git mv`,
иначе история массового переезда потеряется и ревью станет нечитаемым.
**Делаем:** реструктуризация в `services/{core-api,tracker-adapter,bot}` + `libs/contracts`
(см. 01) — через `git mv`, чтобы сохранить историю. Перенос `bot/db/*` и доменных
`bot/services/*` в `core-api/app/{db,domain}`. Перенос alembic в core-api, правка `env.py` на
`app.db.models`. Перенос тест-набора в `core-api/tests`, замена импортов. **Тестовый конфиг:**
корневой `pytest.ini` (`testpaths = tests`, `asyncio_mode=auto`) не подхватится из
`services/core-api` — завести per-service `pytest.ini`/`pyproject` в каждом сервисе (сохранить
`asyncio_mode=auto`) и `conftest.py` рядом с его тестами. Компоуз-каркас (postgres + пустые
core-api/adapter).
**Приёмка:** `cd services/core-api && python -m pytest` — все существующие тесты зелёные (та же
логика, только новые импорты); `alembic upgrade head` на чистой БД проходит; `docker compose
config` валиден; в `git log --follow` виден переезд файлов (mv, не add+delete).
**Зависимость:** нет.

## Фаза 1 — core-api (домен по HTTP)
**Делаем:** FastAPI-скелет (`main.py`, `get_session`, auth Bearer). Роутеры домена
(cars/drivers/invitations/schedules/payments/reports/assistant/me) поверх перенесённого домена.
Перенос ИИ-распознавания в `clients/ai_gateway.py` + `POST /payments/recognize`. `libs/contracts`
DTO. Контрактные тесты (httpx ASGITransport).
**Приёмка:** все домен-эндпоинты отвечают; unit-домен зелёный; контрактные тесты на CRUD/оплату/
график/отчёты зелёные; `GET /me` возвращает роли корректно.
**Зависимость:** Фаза 0.

## Фаза 2 — Бот как тонкий клиент
**Делаем:** `ApiClient`, переписать все 10 хендлеров, `RoleMiddleware` без БД (роль через API),
джобы планировщика через API (reminders_plan/mark). Убрать из бота БД и домен. Тесты бота на
моках `ApiClient`.
**Приёмка:** бот поднимается только с `CORE_API_URL`/`CORE_API_TOKEN` (без DATABASE_URL);
сквозной прогон основных сценариев (регистрация, график, оплата с чеком, отчёты, «спросить ИИ»)
против запущенного core-api даёт поведение, совпадающее с эталоном (`QA_ИНСТРУКЦИЯ.md`);
dispatch-тесты зелёные.
**Зависимость:** Фаза 1. После этой фазы платформа функционально = старому боту, но через API.

## Фаза 3 — Адаптер + телеметрия (req 1,3,4)
**Предусловие (для живой проверки без авто):** поднять тестовый поток через Traccar Client
(OSMAnd) — **открыть порт 5055/tcp на сервере Traccar и в Security Group/файрволе** (в пилоте не
открывался, см. 09) и завести устройство в Traccar. Без этого фаза встанет на проверке ингеста.
**Делаем:** миграция `0006_tracking`. `tracker-adapter`: `TrackerProvider` +
`TraccarProvider` (REST+WS), ингест-воркер, command-API, health. core-api:
`POST /telemetry/batch` (запись telemetry + обновление car_state + одометр), `GET /cars/{id}/
state`, `/telemetry`, привязка `PUT /cars/{id}/tracker`. Бот: экран «Где машина» + привязка
трекера админом.
**Приёмка (без железа — машины 139 уже нет на нашем Traccar, см. ниже «Железо»):**
провайдер-тесты `TraccarProvider` на моках REST/WS зелёные; **живой ингест проверяется через
Traccar Client (OSMAnd) на телефоне** — точки идут в `telemetry`, `car_state` обновляется
(позиция/online; зажигание/пробег/бит27 у телефона не будет — только гео); бот показывает живую
позицию и историю.
**Зависимость:** Фаза 1 (для core-api эндпоинтов). Может идти параллельно Фазе 2 в части адаптера.

## Фаза 4 — Штрафы и ТО (req 5, данные)
**Делаем:** миграция `0007_fines_maintenance`. core-api: CRUD `fines`, `maintenance_items`,
`maintenance/{type}/done`; обновление одометра ТО из телеметрии. Бот: экраны ввода штрафа и
ТО (админ), кнопка «ТО выполнено».
**Приёмка:** админ заводит штраф и интервал ТО; одометр из телеметрии виден в карточке машины;
unit-тесты доменной логики штрафов/ТО зелёные.
**Зависимость:** Фаза 3 (одометр из телеметрии).

## Фаза 5 — Движок правил + алерты + блокировка (req 5)
**Делаем:** миграция `0008_rules_alerts_commands`. core-api: `rules` CRUD, `engine.py`+три
эвалуатора, `alerts` API, `commands` API с защитным гейтом, `clients/adapter.send_command`.
Бот: опрос алертов, карточка с кнопкой «Заблокировать»/«Разблокировать» (`BlockCB`).
**Приёмка (логика, без железа):** правила overdue/fines/maintenance создают алерты (без дублей
благодаря частичному uniq-индексу, авто-resolve при снятии условия); бот показывает алерт админу
с кнопкой; блокировка проходит только при «стоит (speed<1уз ∧ motion=false) + зажигание off +
online», иначе `blocked_by_safety` с понятным сообщением; двойное нажатие не даёт двух команд;
`requested_by` проверяется на сервере (только ADMIN_IDS); всё пишется в `commands`; водитель
уведомляется; переход `sent→acked` — по телеметрии с битом 27 в окно, иначе «не подтверждено» с
предупреждением. Тесты гейта/эвалуаторов/дедупа/idempotency зелёные (на моке adapter-клиента).
**Железный E2E — отдельная веха (Фаза 5-HW), внешняя зависимость:** требует получить номер SIM
машины с подтверждённым реле (пока это только 139) и переключить её на наш Traccar
(`8040000 <ip> 5013`), затем на **стоящей** машине: алерт → кнопка → `engineStop` → `S20,OK` →
`engine_blocked` по биту 27 → разблокировка. Планировать, когда авто и SIM доступны.
**Зависимость:** Фазы 3 и 4 (для 5-HW — ещё и внешняя: доступ к авто + SIM).

## Фаза 6 — Харднинг
**Делаем:** аутентификация сервис-к-сервису (раздельные `CORE_API_TOKEN`/`INGEST_TOKEN`/
`ADAPTER_TOKEN`, ротация), деплой-конфиги (адаптер отдельно рядом с Traccar; прод-Traccar MySQL —
compose с сервера `~/traccar/`, состав сверить на месте), ретеншен/чистка
телеметрии, логирование/метрики/health, docs развёртывания, ретраи/бэкоффы ингеста и клиентов.
**Приёмка:** compose поднимает всё; перезапуск любого сервиса не теряет данные; ингест переживает
разрыв Traccar; чистка телеметрии работает; прод-конфиг задокументирован.
**Зависимость:** Фазы 1–5.

## Общие критерии готовности (Definition of Done, каждая фаза)
- `python -m pytest` (в затронутых сервисах) зелёный; новые тесты добавлены.
- Миграции применяются на чистой БД и на копии текущей; `test_app`-пиннинг обновлён.
- Одна ветка/коммит на подзадачу; ревью AlterEgoNurs.
- Нет прямого доступа бота к БД (после Фазы 2); нет угаданных фактов о Traccar (только из 09).
