# Функциональные требования

## Telegram-бот управления автопарком: регистрация водителей и учёт платежей

**Версия:** 1.0 (черновик)
**Дата:** 2026-07-04
**Статус:** На согласовании
**Тип документа:** Функциональные требования (ФТ). Техническое задание и технические требования в данный документ не входят.

---

## 1. Назначение и цель продукта

### 1.1. Бизнес-контекст

Существует автопарк, принадлежащий владельцу. В автопарке есть автомобили, на каждом из которых установлен GPS-трекер с функцией дистанционного управления двигателем (включение/выключение) и отслеживания местоположения. Автомобили передаются водителям в аренду. Водитель обязан вносить арендную плату по установленному графику. При просрочке платежа автомобиль может быть дистанционно заглушён.

### 1.2. Цель первого этапа

Настоящий документ описывает **первый этап** автоматизации, ограниченный двумя ключевыми процессами:

1. **Автоматизация регистрации водителей** — приём водителей в систему по приглашению, привязка к конкретному автомобилю, сбор персональных данных.
2. **Фиксация платежей** — приём чеков об оплате, их распознавание с помощью ИИ и подтверждение факта оплаты.

> **Важно (границы этапа).** Управление GPS-трекерами (дистанционное включение/выключение двигателя, отслеживание местоположения) в данный этап **не входит** и в настоящих функциональных требованиях не описывается. Первый этап создаёт учётную базу (водители, автомобили, платежи), на которую будет опираться последующая интеграция с трекерами.

### 1.3. Реализация

Продукт реализуется в виде **Telegram-бота**. Все взаимодействия пользователей происходят внутри бота.

## 2. Роли пользователей

| Роль | Кто это | Способ назначения | Ключевые возможности |
|------|---------|-------------------|----------------------|
| **Администратор (Владелец)** | Владелец автопарка и доверенные лица | Только через переменные окружения бота на этапе запуска | Полный контроль: графики, суммы, статусы оплат, аналитика через ИИ |
| **Водитель** | Арендатор автомобиля | Регистрация в боте **только по одноразовой ссылке-приглашению** от администратора | Регистрация по приглашению, внесение платежей (чеки) |
| **Неавторизованный (Чужой)** | Любое лицо без приглашения | — | Никаких. Взаимодействие с ботом заблокировано |

### 2.1. Требования к роли «Администратор»

- **FR-ADM-1.** Список администраторов задаётся **исключительно через переменные окружения** бота в момент запуска. Это исключает возможность получить права администратора через интерфейс бота.
- **FR-ADM-2.** Система должна поддерживать **несколько администраторов** (двое, трое и более), указанных в переменной окружения.
- **FR-ADM-3.** Ни при каких условиях назначить или снять администратора через сам бот нельзя — только изменением переменной окружения и перезапуском.

### 2.2. Требования к роли «Водитель»

- **FR-DRV-1.** Водителем может стать только пользователь, перешедший по одноразовой ссылке-приглашению, сгенерированной администратором (см. 3.1).
- **FR-DRV-2.** До завершения регистрации водитель имеет доступ только к сценарию регистрации.

### 2.3. Требования к контролю доступа

- **FR-ACC-1.** Взаимодействие с ботом (регистрация) возможно только при переходе по действительной одноразовой ссылке-приглашению. Лицо без приглашения не может зарегистрироваться или иным образом взаимодействовать с функциональностью.
- **FR-ACC-2.** Неавторизованному пользователю выводится нейтральное сообщение об отсутствии доступа, без раскрытия внутренней информации.

## 3. Функциональные требования по процессам

### 3.0. Управление автопарком (справочник автомобилей)

- **FR-CAR-1. Ввод автомобиля.** Администратор добавляет автомобили в систему через бот.
- **FR-CAR-2. Фото автомобиля.** При добавлении администратор прикрепляет **фотографию** автомобиля.
- **FR-CAR-3. Атрибуты.** Для автомобиля указываются идентифицирующие данные (например, гос. номер, марка/модель) и фото.
- **FR-CAR-4. Статус.** Каждый автомобиль имеет статус: **свободен** / **занят** (закреплён за водителем).
- **FR-CAR-5. Управление списком.** Администратор может просматривать список автомобилей и их статусы, редактировать и удалять записи.

### 3.1. Приглашение и регистрация водителя

**Сценарий инициируется администратором.**

- **FR-INV-1. Создание приглашения.** Администратор нажимает кнопку **«Новый водитель»**.
- **FR-INV-2. Выбор автомобиля админом.** Администратор сам выбирает автомобиль для нового водителя из числа **свободных**. Занятые автомобили для выбора недоступны.
- **FR-INV-3. Генерация ссылки.** Бот генерирует **одноразовую ссылку** с встроенным одноразовым кодом, привязанную к выбранному автомобилю. Администратор передаёт ссылку водителю.
- **FR-INV-4. Переход по ссылке.** Водитель переходит по ссылке — открывается бот, автоматически подставляется команда с одноразовым кодом, открывается форма регистрации.
- **FR-INV-5. Одноразовость и срок действия.** Ссылка/код действительны для одной регистрации и в течение **24 часов** с момента создания. Ссылка становится недействительной после использования либо по истечении 24 часов — в зависимости от того, что наступит раньше.
- **FR-REG-1. Сбор данных.** В форме регистрации водитель вводит:
  - Фамилию, имя, отчество (ФИО);
  - Номер телефона;
  - **ИНН** (данные паспорта **не запрашиваются и не хранятся**);
  - **Селфи** (фотографию).
- **FR-REG-2. Завершение.** После отправки селфи система регистрирует водителя и закрепляет за ним автомобиль из приглашения. Автомобиль переходит в статус «занят».
- **FR-REG-3. Защита от двойной привязки.** Один автомобиль не может быть закреплён более чем за одним водителем. Привязка задаётся на этапе приглашения (FR-INV-2), что исключает конкуренцию за одну машину.
- **FR-REG-4. Уведомление администратора.** О факте новой регистрации уведомляется администратор.

> **Примечание.** Поскольку автомобиль выбирает администратор при создании приглашения, водитель машину не выбирает. Требование о скрытии арендатора занятых машин от водителя более неактуально — водитель списка машин не видит вовсе.

> **Открытые вопросы по регистрации:**
> - Нужна ли валидация формата номера телефона и ИНН?
> - Что происходит, если водитель прервал регистрацию на середине (можно ли повторно открыть форму по той же ссылке в течение 24 часов)?
> - Может ли администратор отозвать/пересоздать приглашение до его использования?

### 3.2. График и суммы платежей

- **FR-SCH-1.** У каждого водителя есть **индивидуальный график платежей**.
- **FR-SCH-2.** График платежей и суммы платежей устанавливаются и регулируются **администратором** (владельцем).
- **FR-SCH-3. Гибкая периодичность.** Периодичность платежей задаётся гибко (например: ежедневно, еженедельно, ежемесячно или произвольный интервал/даты) индивидуально для каждого водителя.
- **FR-SCH-4.** Администратор может назначить/изменить сумму платежа для конкретного водителя.
- **FR-SCH-5.** Администратор может видеть, кто и сколько оплатил, и корректировать статусы оплат.

> **Открытые вопросы по графику:**
> - Какие именно варианты периодичности нужны в интерфейсе (готовые пресеты + произвольный ввод)?
> - Логика при частичной оплате / переплате / просрочке?

### 3.3. Внесение платежа водителем

- **FR-PAY-1. Инициация.** Водитель через интерфейс бота (кнопки) выбирает действие «Произвести оплату».
- **FR-PAY-2. Запрос чека.** Бот отображает форму с просьбой отправить чек об оплате.
- **FR-PAY-3. Отправка чека.** Водитель совершает оплату через мобильное приложение банка и отправляет чек (фото/скриншот/документ) в бот.
- **FR-PAY-4. Признание оплаты.** Отправленный и подтверждённый чек признаётся системой как факт оплаты (после подтверждения через ИИ — см. 3.4).

### 3.4. Распознавание чека с помощью ИИ

- **FR-AI-1. Технология.** На начальном этапе распознавание работает на базе **подписки Claude (ИИ)**.
- **FR-AI-2. Чтение чека.** При отправке чека ИИ считывает его содержимое.
- **FR-AI-3. Обратный ответ и проверка.** После распознавания ИИ формирует ответ водителю с извлечёнными данными: **сумма оплаты, дата/время платежа** и прочие реквизиты — и спрашивает: «Вы оплатили такую-то сумму, время такое-то. Всё верно?».
- **FR-AI-4. Подтверждение.** Если водитель подтверждает («Да, всё верно»), система фиксирует платёж и отправляет информацию об оплате дальше.
- **FR-AI-5. Уведомление владельцу.** В момент подтверждения администратору (владельцу) приходит уведомление: **какой водитель**, **какую сумму** оплатил, и **сам чек**.

> **Открытые вопросы по ИИ-распознаванию:**
> - Действия при ошибочном распознавании (водитель говорит «неверно») — повторная отправка, ручной ввод, отправка на ручную проверку админу?
> - Защита от повторной отправки одного и того же чека (дубликаты).
> - Защита от поддельных / отредактированных чеков.

### 3.5. Отчёты и аналитика для владельца

Администратору доступны как **кнопочные отчёты** (основной способ), так и **свободные запросы к ИИ** (дополнительно).

**Кнопочные отчёты (обязательно):**

- **FR-RPT-1. Список машин с водителями.** Отчёт со всеми автомобилями и закреплёнными за ними водителями. Если водитель есть — показывается; если машина свободна — помечается как свободная.
- **FR-RPT-2. Приближающиеся платежи.** Список водителей, которым в ближайшее время (по графику) предстоит внести оплату.
- **FR-RPT-3. Выписка по оплатам.** Выписка по платежам с возможностью просмотра **по машинам** и **по водителям** (кто, когда, сколько оплатил).

**Свободные запросы к ИИ (дополнительно):**

- **FR-AI-6.** Администратор может писать ИИ-инструменту произвольные запросы и получать сводную информацию (кто оплатил / не оплатил, у кого подошёл срок, сколько машин занято/свободно и т. п.).
- **FR-AI-7.** Ответы (и отчёты, и ИИ) формируются на основании актуальных данных системы (водители, автомобили, платежи, графики).

## 4. Данные, которыми оперирует система

> Перечень сущностей и атрибутов на уровне бизнес-анализа. Модель данных детализируется на этапе технического проектирования.

| Сущность | Ключевые атрибуты (бизнес-уровень) |
|----------|-------------------------------------|
| **Автомобиль** | Идентификатор/гос. номер, марка/модель, **фото**, статус (свободен / занят), закреплённый водитель |
| **Водитель** | ФИО, номер телефона, **ИНН** (паспорт не хранится), **селфи**, Telegram-ID, закреплённый автомобиль, дата регистрации |
| **Администратор** | Telegram-ID (из переменных окружения) |
| **Приглашение** | Одноразовый код/ссылка, привязанный автомобиль, время создания, срок действия (24 часа), статус (активно / использовано / истекло) |
| **График платежей** | Привязка к водителю, гибкая периодичность/даты, сумма платежа |
| **Платёж** | Водитель, сумма, дата/время, чек (файл), статус, распознанные ИИ данные |

> **Хранение данных.** Персональные данные (ИНН, селфи) и файлы (фото автомобилей, чеки) хранятся на сервере. Паспортные данные не собираются и не хранятся.

## 5. Ключевые бизнес-правила

- **BR-1.** Регистрация доступна только по одноразовой ссылке-приглашению от администратора.
- **BR-2.** Права администратора выдаются только через переменные окружения; получить их через бот невозможно.
- **BR-3.** Один автомобиль — один активный водитель.
- **BR-4.** Автомобиль для водителя выбирает администратор при создании приглашения; водитель список машин не видит.
- **BR-5.** Паспортные данные не собираются; из идентификаторов хранится только ИНН.
- **BR-6.** Платёж считается принятым только после подтверждения водителем распознанных ИИ данных.
- **BR-7.** О каждом принятом платеже владелец получает уведомление с чеком.

## 6. Границы первого этапа (Scope)

**Входит в этап:**
- Контроль доступа (одноразовые ссылки-приглашения / администраторы).
- Управление справочником автомобилей администратором (ввод с фото).
- Приглашение и регистрация водителей с привязкой к автомобилю.
- Индивидуальные графики и суммы платежей, управляемые администратором.
- Приём чеков и распознавание платежей с помощью ИИ (Claude).
- Уведомления владельцу о платежах.
- Кнопочные отчёты для владельца (машины+водители, приближающиеся платежи, выписка по оплатам).
- Дополнительно — аналитические запросы владельца к ИИ.

**Не входит в этап (последующие этапы):**
- Интеграция с GPS-трекерами (дистанционное включение/выключение двигателя, геолокация).
- Автоматическое отключение автомобиля при просрочке.
- Онлайн-приём платежей / эквайринг (на первом этапе оплата вне системы, в бот отправляется только чек).
- Полноценная бухгалтерия/отчётность за пределами перечисленного.

## 7. Предположения и зависимости

- **A-1.** Наличие активной подписки Claude (ИИ) для распознавания чеков и аналитики.
- **A-2.** Наличие инфраструктуры для запуска и хостинга Telegram-бота, включая безопасное хранение переменных окружения.
- **A-3.** Водители имеют доступ к Telegram и мобильному банковскому приложению для оплаты.
- **A-4.** Персональные данные (ФИО, телефон, ИНН, селфи) хранятся на сервере с учётом требований по защите персональных данных. Паспортные данные не собираются.

## 8. Открытые вопросы для согласования с заказчиком

1. **Параметры графика платежей** — набор вариантов периодичности в интерфейсе; обработка просрочек и частичных оплат.
2. **Обработка ошибок распознавания чека** и защита от дубликатов/подделок.
3. **Валидация данных** (формат телефона, ИНН).
4. **Может ли админ отозвать/пересоздать** приглашение до его использования?
5. **Требования к защите персональных данных** (ИНН, селфи) и соответствие законодательству.
6. **Языки интерфейса** бота.
7. **Валюта** платежей.

> **Решено с заказчиком:** приглашение — через кнопку «Новый водитель» с выбором машины админом и одноразовой ссылкой сроком действия **24 часа**; автопарк заводит админ с фото; периодичность графика — гибкая; паспорт не хранится (только ИНН и селфи), данные на сервере.

## 9. Критерии приёмки (верхнеуровневые)

- Чужой пользователь без действительной ссылки не может ничего сделать в боте, кроме получения сообщения об отказе.
- Администратор заводит автомобиль в систему с фотографией.
- Администратор нажимает «Новый водитель», выбирает свободную машину, получает одноразовую ссылку.
- По ссылке водитель проходит регистрацию: ввод данных (ФИО, телефон, ИНН) → селфи → успешная регистрация, машина закреплена.
- Ссылка недействительна после использования или по истечении 24 часов.
- Администратор (из переменных окружения) видит список водителей с автомобилями, задаёт им гибкие графики и суммы, видит статусы оплат.
- Водитель отправляет чек, ИИ распознаёт сумму и время, водитель подтверждает, платёж фиксируется.
- Владелец получает уведомление о платеже с чеком.
- Владелец кнопками открывает отчёты: список машин с водителями, приближающиеся платежи, выписку по оплатам (по машинам и по водителям).
- Дополнительно владелец получает от ИИ корректные ответы на свободные запросы.
