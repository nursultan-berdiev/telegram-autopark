## Context

По продукту утверждены функциональные требования (см. `Функциональные_требования.md`). Реализован **Этап 1**: регистрация водителей по приглашению и учёт платежей с ИИ-распознаванием чеков. Управление GPS-трекерами и онлайн-эквайринг — вне этого этапа.

**Стек (утверждён):** Python + aiogram (v3), PostgreSQL, интеграция с Claude API для чтения чеков и свободной аналитики.
**Стратегия:** последовательно по модулям, релиз одним куском в конце Этапа 1.
**Оценка целиком:** ≈ 26–36 рабочих дней (≈ 6–7 недель на одного разработчика уровня middle+).

---

## Технологические решения

- **Bot framework:** `aiogram` 3.x (async, FSM для форм регистрации/ввода машин).
- **БД:** PostgreSQL + `SQLAlchemy` (async) + `Alembic` для миграций.
- **ИИ:** `anthropic` SDK, модель `claude-opus-4-8`. Чек передаётся как изображение (vision), данные возвращаются через tool use (принудительный вызов `report_receipt`).
- **Конфигурация:** переменные окружения (`.env` + `pydantic-settings`). Список админов — только через env (`ADMIN_IDS`), несколько через запятую.
- **Хранение файлов:** фото машин, селфи, чеки — на сервере (локальная папка `FILES_DIR` + путь в БД). Telegram `file_id` хранится для повторной выдачи.
- **Деплой:** сервер заказчика (systemd-сервис или Docker Compose: бот + Postgres). Long-polling на старте (webhook — опционально позже).

> **Окружение (важно!):** venv собирать только через **uv с managed 64-битным Python 3.12**:
> `uv venv --python-preference only-managed --python 3.12 .venv`. Системный
> `py -3.14` ломает сборку wheel (pydantic-core/asyncpg/greenlet), системный
> `py -3.12` — 32-битный (нет wheel для greenlet).

### Схема БД (реализована)

| Таблица | Ключевые поля |
|---------|---------------|
| `cars` | id, plate (uniq), model, photo (file_id+path), status (free/occupied), created_at |
| `drivers` | id, tg_user_id (uniq), full_name, phone, inn, selfie (file_id+path), car_id (FK), created_at |
| `invitations` | id, code (uniq), car_id (FK), created_by, expires_at (created+24ч), status (active/used/expired), used_by |
| `payment_schedules` | id, driver_id (FK, uniq), period (enum), interval_days, amount, next_due_date, active |
| `payments` | id, driver_id (FK), car_id, amount, paid_at, receipt (file_id+path), receipt_hash (dedup), recognized_data (JSON), status, created_at |

## Этапы реализации

### ✅ Этап 0 — Каркас и инфраструктура
Структура aiogram, конфиг через env, PostgreSQL+SQLAlchemy async+Alembic (миграция `0001_initial`), middleware ролей (админ/водитель/гость), `/start`.
Файлы: `bot/__main__.py`, `bot/config.py`, `bot/db/`, `bot/middlewares/role.py`, `bot/handlers/start.py`, `alembic/`.

### ✅ Этап 1 — Управление автопарком (FR-CAR-1..5)
FSM добавления машины (номер → модель → фото), список со статусами, удаление (с защитой занятых).
Файлы: `bot/services/cars.py`, `bot/handlers/cars.py`, `bot/keyboards/cars.py`, `bot/states/car.py`.

### ✅ Этап 2 — Приглашение и регистрация водителя (FR-INV-1..5, FR-REG-1..4)
Кнопка «Новый водитель» → выбор свободной машины → deep-link `t.me/bot?start=<code>` сроком 24ч. Валидация кода (активен/не истёк/не использован, ленивое протухание). FSM регистрации (ФИО → телефон → ИНН → селфи; паспорт не запрашивается). Занятость машины + уведомление админу.
Файлы: `bot/services/invitations.py`, `bot/services/drivers.py`, `bot/handlers/new_driver.py`, `bot/handlers/registration.py`, `bot/states/registration.py`.

### ✅ Этап 3 — Графики и суммы платежей (FR-SCH-1..5)
Гибкая периодичность (день/неделя/месяц/произвольный интервал) + сумма. Расчёт `next_due_date` с корректировкой конца месяца, сдвиг после оплаты.
Файлы: `bot/services/schedules.py`, `bot/handlers/schedules.py`, `bot/keyboards/schedules.py`, `bot/states/schedule.py`.

### ✅ Этап 4 — Приём платежей + ИИ-распознавание чеков (FR-PAY-1..4, FR-AI-1..5) ⚠️ ключевой
Кнопка «Оплатить» → чек → Claude vision (сумма/дата/время через tool use) → подтверждение «Всё верно?» → фиксация платежа, сдвиг графика, уведомление владельцу с чеком. Защита от повторной отправки чека по SHA-256 хешу. Обработка ошибок распознавания.
Файлы: `bot/services/ai.py`, `bot/services/payments.py`, `bot/handlers/payments.py`, `bot/keyboards/driver_menu.py`, `bot/states/payment.py`.

### ✅ Этап 5 — Кнопочные отчёты для владельца (FR-RPT-1..3)
Машины + водители (свободные помечены); «кому скоро платить» (сорт. по дате, метка просрочки); выписка по оплатам по водителям и по машинам.
Файлы: `bot/services/reports.py`, `bot/handlers/reports.py`, `bot/keyboards/reports.py`.

### ✅ Этап 6 — Свободные ИИ-запросы владельца (FR-AI-6/7)
Кнопка «Спросить ИИ» → свободный вопрос → компактный снимок данных БД → ответ Claude на основе актуальных данных.
Файлы: `bot/handlers/ai_query.py`, `bot/services/ai.py::answer_owner_query`, `bot/services/reports.py::build_snapshot`.

### ✅ Этап 7 — Тестирование, стабилизация, приёмка
pytest-набор (22 теста, async SQLite в памяти) во `tests/`, dry-run сборки диспетчера. Осталось: E2E на боевом окружении.

## Верификация (как проверять на боевом окружении)

- **Роли (Э0):** зайти админом (из env) и «чужим» — разное поведение; отказ для неизвестного.
- **Автопарк (Э1):** добавить машину с фото → проверить запись и файл; статус «свободна».
- **Регистрация (Э2):** сгенерировать ссылку → регистрация с другого аккаунта → машина «занята», админу пришло уведомление; повторный переход по использованной/просроченной ссылке — отказ.
- **Графики (Э3):** назначить график с разной периодичностью → проверить `next_due_date`.
- **Платежи+ИИ (Э4):** отправить реальный чек → ИИ вернул сумму/время → подтвердить → владельцу пришло уведомление с чеком; тот же чек повторно — защита срабатывает.
- **Отчёты (Э5):** сверить три отчёта с данными в БД.
- **ИИ-запросы (Э6):** «кто не оплатил» / «сколько машин свободно» — ответ совпадает с БД.

**Модульные тесты (уже проходят):** `python -m pytest` → 22 passed.

## Открытые вопросы (уточнить с заказчиком)
1. Логика **просрочки и частичной оплаты** в графиках (сейчас график просто сдвигается на период после каждой подтверждённой оплаты).
2. Поведение при **ошибке распознавания чека** и защита от подделок (сейчас: «неверно» → повтор; дубликаты блокируются по хешу).
3. **Валюта** и **язык** интерфейса (сейчас RU, валюта — как на чеке).
4. Может ли админ **отозвать/пересоздать** приглашение до использования (сейчас нет — только истечение 24ч или использование).
